# 前端技术栈选型决策树

## 决策流程

```
目标平台是什么？
├─ Web 浏览器
│   ├─ 项目规模大 / 组件化要求高 / 团队有 React 经验 → React
│   └─ 中小规模 / 快速交付 / 团队有 Vue 经验 → Vue
├─ iOS + Android 双端 → Flutter
├─ Windows / macOS 桌面 → Electron
└─ 微信生态 → 小程序（原生框架）
```

## 对比表

| 维度 | React | Vue | Flutter | Electron | 小程序 |
|---|---|---|---|---|---|
| 目标平台 | Web | Web | iOS/Android | 桌面 | 微信 |
| 学习曲线 | 中 | 低 | 中 | 低（有 Web 基础） | 低 |
| 生态 | 最大 | 大 | 中大 | 大 | 封闭但全 |
| 性能 | 高 | 高 | 接近原生 | 中（内存占用高） | 受平台限制 |
| 适用规模 | 中大型 | 中小型 | 中大型 | 中小型 | 轻量 |
| 包体积 | 小 | 小 | 较大 | 大 | 平台限制 2M 主包 |

## 默认规则

1. **未指定栈 + Web 场景 → React**；
2. **项目已有栈 → 延续**，不擅自引入新栈；确需引入须在技术方案论证并告知后端与测试（影响构建与联调方式）；
3. **跨端优先**：同一产品需要 iOS + Android 时优先 Flutter，不分别为双端写两套原生；
4. **小程序约束优先**：包体积、审核规则、setData 性能在小程序规范中单独约束，见 `miniprogram.md`。

## 反模式

- 一个页面混用多种框架；
- 为"赶时髦"在存量项目中途换栈；
- 忽略包体积与审核约束直接按 Web 思路写小程序。
