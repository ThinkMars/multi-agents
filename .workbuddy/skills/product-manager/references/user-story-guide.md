# 用户故事编写指南

## 格式

```
作为 <角色>，
我希望 <功能>，
以便 <价值>。
```

示例：作为一个健忘的上班族，我希望在手机上记录待办事项，以便不漏办重要工作。

## INVEST 原则

| 原则 | 含义 | 自检问题 |
|---|---|---|
| I 独立 | 故事间尽量解耦，避免相互依赖 | 拆分后是否还有强依赖？ |
| N 可协商 | 故事是对话的起点，不是合同条款 | 细节是否可以与研发讨论？ |
| V 有价值 | 对用户或业务有可感知的价值 | 删掉它用户会受影响吗？ |
| E 可估算 | 工作量可被研发评估 | 研发能给出粗略工期吗？ |
| S 小 | 一个迭代内能完成 | 是否超过 1/3 迭代容量？ |
| T 可测试 | 有明确验收标准 | 能写出 Given/When/Then 吗？ |

## 拆分方法

1. **按用户操作流拆分**：创建 → 查看 → 编辑 → 删除 → 搜索；
2. **按角色拆分**：管理员故事与普通用户故事分开；
3. **按数据变体拆分**：正常数据 / 空数据 / 极限数据；
4. **按平台拆分**：Web 端与移动端分开估算；
5. **纵向拆分优先**：每个故事都产出可用的端到端功能，避免按技术层横向拆（"先做所有接口"是反模式）。

## 常见反模式

- 按技术任务写故事（"开发数据库层"）——没有用户价值；
- 故事过大（"做一个完整的电商系统"）——无法估算与验收；
- 只写 happy path——异常路径缺失导致返工。
